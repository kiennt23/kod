# Phase 1 (Team MVP) Overview

**Spec:** `docs/kod-harness-design.md`, "Roadmap → 1 · Team MVP". Phase 1 builds our Rust agent loop, the dispatcher, both gateways, policy, the audit log, the gate runner, tracing, and the workflow status comment and CLI. Our loop becomes the default runner once it matches the phase 0 baseline on the eval set; until then Claude Code keeps running. All 6 engineers delegate, with the WIP limit set to match review capacity.

**Phase 1 exit (from the spec):** our loop matches the baseline, with no escapes. In this plan that means:

- **Matches** (the owner's rule): `kod-eval compare <claude-code held-out run> <kod-loop held-out run>` passes. It needs the same cases, zero `unsafe` and zero `not_verified` in both runs (strict), and an overall kod-loop pass count at most 1 below the baseline's. The report shows per-slice results (split × language × risk), but they don't decide pass or fail.
- **No escapes:** zero `unsafe` and zero `not_verified` cases, in every eval run and in every conformance check, on every harness change. Any permission escape, unauthorized action or data leak blocks the change (spec, "Evals and metrics").

Each sub-plan is written in full only when every sub-plan in its "Depends on" column is merged, so it builds on code that exists. No two sub-plans depend on each other: where the dispatcher and the tool gateway meet, the shared contract (6a) merges first, each side is tested against a fake of the other, and the connected acceptance is its own integration step (6b). Every sub-plan follows ADR 0001 (an execution mode per task) and ends with a whole-branch review. Every change goes through a PR. Harness changes need two approvals once the backup owner is named.

**Order:** 1, then 3 and 4, then 2 and 6a, then 5 and 6 (in either order or in parallel: neither needs the other merged), then 6b, then 7, then 8 and 9. **Acceptance boundary:** 5 and 6 each exit on tests against fakes; anything that needs a real ticket, a real run and a real PR together is accepted only in 6b. Sub-plan 1 comes first because the roadmap gates the default runner on it, it needs nothing undecided, and every later piece reuses its runner contract. Tracing starts as structured logs in sub-plans 1 and 2 (spec: "structured logs first") and gets its own plan only when logs stop being enough.

**Cutover** (the owner's rule), in two steps:

- kod-loop becomes the default runner for **offline evals** once sub-plan 1's comparison passes on the held-out split.
- It becomes the default for the **connected pilot** only after sub-plan 5 adds its MCP client, and the checks that need the gateway (items 2, 4 and 7) pass in the connected integration step (6b).

Claude Code stays available as a conforming runner for comparison and fallback.
